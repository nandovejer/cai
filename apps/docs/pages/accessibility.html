LUZ aims for WCAG 2.2 level AA. What is checked on every change, what has not been tested, and the known issues. Last reviewed on 15 October 2026.

Target

LUZ aims to meet WCAG 2.2 level AA, the level that EN 301 549 and the European Accessibility Act refer to.

A design system cannot make a service accessible by itself: how you use the components decides the result. Each component page says what is yours to do, under Keyboard and ARIA and Writing the content.

What is checked on every change

  • An automated scan with axe-core of the home page, in English, Spanish and Arabic, and of every page of the documentation, in the light, dark and high-contrast modes. On component and pattern pages the scan runs once with each tab open, and on a sample of pages once with the search dialog open, with results and with none. A serious or critical finding fails the build.
  • Keyboard use of the sidebar drawer, the modal dialog, the tabs, the Code and Design tabs of the component pages, the "On this page" index, whose links open the tab of the section they point at, and the search: Ctrl+K, the arrow keys through the results, Enter and Escape.
  • The pages with JavaScript turned off: content is readable at 320 pixels wide, the Code and Design sections of a component page show one after the other, the search button is a link to the A–Z index, and no control that needs JavaScript is left on screen doing nothing. The color mode switcher in the page footer shows as three radio buttons, which still set the mode. The language switch of the home page opens its list of languages, which are links, with the popover API and no script.
  • Reduced motion: no transition or animation runs when the visitor asks for less motion.
  • The timeline: its keys (arrows, Home and End on the dates, mirrored right to left), the Previous and Next buttons, the names of the buttons, that autoplay is opt-in with a visible Pause / Play button, and that with reduced motion autoplay never starts and the button is not shown.
  • Forced colors: a focused button and a focused search result keep a visible outline, the selected tab keeps its underline, and the search dialog keeps its border.
  • The home page in Arabic, right to left: it must not overflow at 320 pixels wide, with JavaScript or without it.
  • Right-to-left text: the demo of every component, except the player, is laid out with dir="rtl" next to its left-to-right layout. Each element with text, and each control, must sit where the mirror image puts it, and nothing may overflow. The check runs with and without JavaScript.
  • Contrast of the text written for the home and documentation pages, in all three modes.
  • Before this release, the same automated suites ran once in Firefox 155 and in WebKit 26.6 and 27.2 (the engine of Safari), on Linux, and their findings were fixed. They do not run on every change, and neither is a test on macOS or iOS.
  • Contrast of every token pair a component draws, by a script, in the three base modes. A theme of your own is measured by the same script, as the themes page shows.

What has not been tested

  • Screen readers. No assistive technology has been used to test this release: NVDA, JAWS, VoiceOver, TalkBack and Orca have not been tried. Nothing here says a component works with them.
  • Speech recognition and screen magnifier software.
  • Right-to-left text by a person who reads it, or with a screen reader. Only the layout is measured by a script, and the player's controls are not part of that measurement.
  • Zoom to 400 percent by hand. Only the 320 pixel width is measured.
  • Research with disabled people.
  • The accessibility reviewer that @luz-ds/check prints, and luz-check itself. They read source files and give advice; they do not open a page, measure on screen or use assistive technology. A run with no findings does not mean a page is accessible.

Automated tools find only part of the problems. Treat this list as the gap, and test your own pages.

Known issues

  • Tooltip. Escape does not close it. This partly fails WCAG 1.4.13 (Content on hover or focus). Keep tooltips non-essential.
  • Modal. Its buttons use the command and commandfor attributes. In a browser without them, and without JavaScript, the open button does nothing.
  • Player. MIDI needs JavaScript and Web Audio. Without them the player shows a message. On this documentation site, the example video's caption files load only with JavaScript; without it the browser lists the tracks but shows no text.
  • Select. The open list is the browser’s or the system’s, so it looks and sounds different in each. Where the browser supports appearance: base-select (Chrome and Edge 135, Safari 27), LUZ styles the list too, and that list has not been tested with a screen reader yet. It works without JavaScript.
  • Linked card. The link in the title covers the whole card, so the body text cannot be selected with a mouse. Keyboard selection, find in page and screen readers reach it as usual.
  • Table sorted in the browser. The sorted column is exposed with aria-sort on its column header, and each sort is announced in a status message. Tabbing through the headings announces the column name; the sort state is read on the header cell and in the status message. Checked in the Chromium accessibility tree only; not yet tested with NVDA, JAWS, VoiceOver, TalkBack or Orca.
  • Avatar with a photo. If the photo does not load, the browser draws its text alternative inside the box, in capitals, and a long name can spill past it.
  • Code and Design tabs. The tab you chose last opens after the page has loaded, so the content below the tabs can move once.
  • Find in page. In browsers that do not support hidden="until-found" (Safari before 26.2, Firefox before 139), find in page (Ctrl+F) does not find text in the tab that is not open. In Safari 26.2 and later it opens the tab but does not scroll to the match. Open the other tab, or turn JavaScript off to see both.
  • Choose your snippet. Without JavaScript the picker is not in the page, every snippet is shown one after the other, and the index table, whose cells are links to the snippets, is the navigation. With JavaScript the picker replaces the table and shows one snippet, and it announces the snippet shown through its <output>, a status message. The focus stays on the choice you made. That announcement has not been tested with a screen reader.
  • Make it yours, sizes demo. The sizes demo is optional: the table of presets on the page lists the sizes without it. Without JavaScript the demo is not shown, so no control is left on screen doing nothing. With it, the sliders resize the page itself, not a sample, and the Reset sizes button puts the page back; nothing is stored, so a reload does the same. The size knobs change the text and the space of the page; a reader’s own text size is respected, because the scale is in rem and follows the browser’s text size.
  • Search shortcut. Ctrl+K (⌘K on a Mac) opens the documentation search instead of the browser’s own web search box. Use the browser’s address bar to search the web. The shortcut is shown on the search button, does nothing while you type in a text area or editable content, and there is no single-key shortcut. In a one-line text field it still opens the search, so on a Mac it replaces Ctrl+K, “delete to the end of the line”, there. On a site that loads the search with site.js, the search’s own script loads when the page is idle, or when you point at or move to the search: a Ctrl+K pressed before that loads it and then opens the search, after a short wait on a slow connection. On a page without a search, Ctrl+K stays the browser’s.
  • Search. It has not been tested with a screen reader. The number of results is announced once you stop typing. Until its script has loaded, the search is a link to the A–Z index, in the same place; if you are on that link when the script arrives, it stays until you leave it, and the focus is never moved. If the script cannot load, the link stays. Closing the search returns the focus to where it was; if nothing had the focus, as after Ctrl+K on a page just loaded, it goes to the search button, and the next Tab continues from there.
  • Search at 400 percent zoom. The whole search dialog scrolls, so the search field can move out of view while you read the results. Shift+Tab or the Up arrow from the first result brings you back to it.
  • Language switcher. The list of languages opens at a fixed place under the header, not next to its button. Below 360 pixels wide its button shows a globe only; the language’s name is still the button’s accessible name. It has not been tested with a screen reader.
  • Navbar menu. On narrow screens the menu of a navbar, in a landing, CMS or docs header, opens as a panel under the header. If you keep pressing Tab after its last link, focus moves into the page and the panel stays open over it. Press Escape to close it. (WCAG 2.2 success criterion 2.4.12, level AAA; level AA 2.4.11 is met.) Where CSS anchor positioning is supported (Chrome and Edge 125, Safari 26, Firefox 147) the panel opens under the header wherever it ends. In older browsers it opens at the height of a one-row bar at the default text size (--luz-bar-h), from the top of the window: with enlarged text and a header that wraps to a second row, or with a banner above the header before the page scrolls, it can cover part of the header.
  • Submenu. A submenu of a header’s links is a native disclosure: Escape and a click outside do not close it; its own button or opening another one does (several can stay open in Firefox before 130 and Safari before 17.2). From 769 pixels wide an open submenu stays over the top of the page, so if you keep pressing Tab after it, a link behind it can be hidden (WCAG 2.2 success criterion 2.4.11, Focus not obscured, minimum). Press its button to close it. In the narrow menu its links are in the flow and Escape closes the whole menu. It has not been tested with a screen reader.
  • Banner. It cannot be closed. It has no script.
  • Cookie consent. Without JavaScript the banner is not shown, because none of the site's own scripts run either; the cookie policy is a link on every page. With it, the banner shows as a band fixed at the bottom of the window, so nothing on the page moves; it comes first after the skip link in the reading and Tab order, takes no focus when the page loads, does not block the page, and Escape neither answers nor hides it. While it shows, the page keeps room for it at its end and scrolls what Tab reaches above it (WCAG 2.2 success criterion 2.4.11). In a window less than 480 pixels tall it is in the flow at the top of the page instead, so the page moves down when it appears. Its confirmation hides with its Close button, which returns focus to the button that opened the banner or to the main content, or when focus leaves it for the page; a click on an empty part of the page does not hide it. The answer is stored in the browser, not in a cookie. It has not been tested with a screen reader.
  • Sticky header, enlarged text. A sticky header (.o-sticky) keeps a field reached with Tab clear of it by a minimum height. That works at 100 and 200 percent text. At 300 percent text, when the header wraps to several rows, Safari can still leave the field partly under it; Chrome, Edge and Firefox keep it clear. The Layout objects page and the landing and CMS Header pages say how to set the padding for your own header. In Firefox with forced colors the dim layer behind the open menu is not drawn; the panel keeps its border.
  • Band. A band (.luz-band) cuts off whatever sticks out of it above or below, so a tooltip on the first control of a band is clipped at 200 percent text and larger; start the band with its heading. The hover of an outline or ghost button on a band shows no change. In forced colors the band has no tint, only two thin rules above and below it.
  • Prose. A table that is wider than the text column and has no .luz-table-wrap around it makes the whole page scroll sideways on a narrow screen. A long preformatted block scrolls inside itself; give it tabindex="0" and a name, as the code block has, or Safari users cannot scroll it with the keyboard.
  • Meta line. The dots between the facts are hidden from screen readers with alternative text for generated content. In a browser without it (Firefox before 128, Safari before 17.4) a screen reader reads each dot.
  • Lists laid out as a grid, stack or row. Safari does not announce a list whose markers are removed, outside a navigation landmark, as a list. Its items are still read in order, and the headings in them still lead through it.
  • Masthead header (cms). In browsers without CSS anchor positioning, the sections menu of the masthead header opens near the top of the window and covers the publication name and the menu button while it is open. Escape, or a click outside the menu, closes it and returns to the page.
  • Table of contents (cms). The mark on the section in view comes from core's script (data-luz-spy); without it, no link is marked, and the links still work. Next to the text, the contents list the sections at the inline end but come first in the source, so Tab reaches them before the text. It has not been tested with a screen reader.
  • Account list (app). The list of an application's account button is a list of links in a popover, not an ARIA menu: it has no arrow keys, and Tab moves through its links. In browsers without CSS anchor positioning it opens as a sheet at the bottom of the window instead of under the button; Escape, or a click outside it, closes it. The button's name is the initials, then the name, so it reads “AM Ana Martín” at every width. It has not been tested with a screen reader.
  • Dashboard (app). The panels keep the order of the markup, so a wide panel that does not fit in what is left of a row starts the next one and leaves a gap; the reading order and the drawn order are always the same. It has not been tested with a screen reader.
  • Timeline. Without JavaScript it is an ordered list with a line and a dot per item, and every item is visible. With it, only the current card is read and reached with Tab; the other cards are inert. The Previous and Next buttons are named only “Previous” and “Next”: the name does not say which date they lead to. Whether a screen reader announces the card that appears when you change the item has not been tested, and the timeline has not been tested with a screen reader at all. Autoplay is off unless the page asks for it. When it is on, it moves a card every few seconds, and a visible Pause / Play button stops and resumes it. It also holds while the pointer moves over the timeline, while the keyboard focus is inside it, while less than half of it is on screen and while the tab is hidden, and it never starts with reduced motion. While it runs, the card is not announced.
  • Copy button. When the browser refuses to copy, the failure is announced to screen readers, but the button shows no message.

Report a problem

If something does not work for you, open an issue on GitHub and say what you were trying to do, the browser and the assistive technology you use.
