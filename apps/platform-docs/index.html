@cai-ds/platform

App-shell patterns and higher-level layout primitives built on top of CAI core. Use Platform when you are building a web application with a consistent page structure — not when you only need individual components.

Installation

Platform depends on @cai-ds/tokens and @cai-ds/core. Load all three in order.

HTML (CDN)

<!-- 1. Tokens (always first) -->
<link rel="stylesheet" href="https://cdn.jsdelivr.net/npm/@cai-ds/tokens@3.0.0/dist/cai-tokens.css">

<!-- 2. Core components -->
<link rel="stylesheet" href="https://cdn.jsdelivr.net/npm/@cai-ds/core@3.0.0/dist/cai.css">

<!-- 3. Platform app-shell patterns -->
<link rel="stylesheet" href="https://cdn.jsdelivr.net/npm/@cai-ds/platform@3.0.0/dist/platform.css">

<!-- Optional: Core JS behaviors -->
<script type="module" src="https://cdn.jsdelivr.net/npm/@cai-ds/core@3.0.0/dist/cai.js"></script>

<html lang="en" data-theme="minimalist">

</body>

When to use Platform

Platform primitives are opinionated by design. If the pattern doesn't map to your use case, compose with core components directly instead.

Use Platform when
  • Building a web app with a persistent header, main content area, and footer
  • You need consistent spacing and layout across multiple app pages
  • You want skip-links, feature grids, and action containers without writing the scaffolding yourself
  • Both @cai-ds/tokens and @cai-ds/core are already in your project
Skip Platform when
  • You only need individual UI components (buttons, forms, cards) — use @cai-ds/core alone
  • You have your own layout system and only need tokens
  • You are embedding CAI into an existing framework layout (Next.js App Shell, etc.)
  • You are building a standalone widget, not a full-page app

Architecture

Three layers with unidirectional dependencies. A lower layer never imports from a higher one.

Dependency chain

@cai-ds/tokens   ←  primitives + semantic theme variables
      ↓
@cai-ds/core     ←  generic reusable components (buttons, forms, cards…)
      ↓
@cai-ds/platform ←  app shells, layout patterns, higher-level primitives

Rule

Platform can import from core and tokens. Core can import from tokens. Nothing in core or tokens may import from platform. This rule is enforced by convention — there is no bundler that enforces it at build time.

Class reference

All Platform classes are prefixed .cai-platform-. They consume semantic tokens only — never primitive color scales.

Page structure

Class Element Description
.cai-platform-page <body> Root grid (header / 1fr / footer). Sets min-height: 100vh.
.cai-platform-page--gradient <body> Modifier. Adds a radial brand-subtle gradient at the top-left corner. Use on marketing or landing pages.
.cai-platform-skip-link <a> Visually hidden until focused. Jumps to #main-content. Required for keyboard accessibility.
.cai-platform-main <main> Main content area. Grid with gap: --cai-space-10 between sections. Combine with .o-container for horizontal centering.
.cai-platform-content <div> / <main> Padded content wrapper with max-width cap. For app-shell layouts where the sidebar handles its own width.
.cai-platform-section <section> Grid container with vertical gap between child elements. Use as the direct child of .cai-platform-main.

Header & footer

Class Element Description
.cai-platform-page-header <div> / <header> Hero-style page header block with bottom margin. Contains a title and optional lead.
.cai-platform-page-header__title <h1> Heading: heading font, size 3xl, weight 300, tight letter-spacing.
.cai-platform-page-header__lead <p> Subtitle: secondary text color, max-width 600px.
.cai-platform-footer <footer> Flex row (space-between). Includes a top border and vertical padding. Collapses to column on mobile. Combine with .o-container.

Content patterns

Class Element Description
.cai-platform-actions <div> Flex row with wrapping and gap for CTA button groups. Collapses to column on mobile <480px.
.cai-platform-feature-grid <div> 2-column grid for feature cards. Collapses to 1 column on mobile. Place .cai-card elements as direct children.
.cai-platform-command-block <div> Installation/CLI command display. Dark background, mono font. Flex row: command on left, copy button on right.
.cai-platform-command-block__cmd <code> The command text. Mono font, wraps on overflow.
.cai-platform-command-block__prefix <span> Shell prefix character ($, pnpm, etc.). Secondary color, non-selectable.
.cai-platform-image <div> 16:9 frame around a native <picture>. The image fills it; with no image, an abstract placeholder shows, in a night version in dark mode.
.cai-platform-image--4x3, --3x2, --1x1, --21x9, --9x16 <div> Modifiers. Other aspect ratios, each with its own placeholder.

Pattern guidance

When to use each platform pattern, when not to, and how it behaves with a keyboard and a screen reader.

Page shell

.cai-platform-page, --gradient, .cai-platform-main, .cai-platform-content

When to use

For the whole page of an app or a product site: a header, a main area that grows and a footer that stays at the bottom.

When not to use

Inside a component or a card: it sets a full-height grid on its element. Do not nest one page shell inside another. Do not use the gradient variant behind long text, where a flat surface is easier to read.

How it works

Put .cai-platform-page on <body>: a three-row grid (header, main, footer) at least the height of the viewport. Use .cai-platform-main on <main> for a page without a sidebar, or .cai-platform-content for the column next to one. CSS only.

Content guidance

Keep one <main> per page, with an id that the skip link points to. Start it with the page header, so the first heading is the <h1>.

Keyboard and ARIA

No interaction of its own. Landmarks come from the native elements: <header>, <nav>, <main>, <footer>. Do not add role to them.

Known issues

None known.

Skip link

.cai-platform-skip-link

When to use

On every page that has navigation or a header before the main content.

When not to use

As the only way to reach the content: the page still needs a logical heading order and landmarks.

How it works

A normal link to the id of <main>, first in <body>. It sits off screen and slides in when it receives focus. The browser does the jump; no JavaScript.

Content guidance

Say where it goes: "Skip to main content". Do not add other text.

Keyboard and ARIA

Tab once from the top of the page to reveal it; Enter follows it and moves focus to the main area. Under reduced motion it appears without sliding.

Known issues

None known.

Page header

.cai-platform-page-header, __title, __lead

When to use

At the top of a page or a main view, to give its title and one sentence about what it is for.

When not to use

For the title of a section inside the page: use a plain heading of the right level. Do not use it twice on one page.

How it works

A wrapper with a title and an optional lead paragraph. The title is the page's <h1>; the class only changes how it looks.

Content guidance

The title names the page in a few words, in sentence case. The lead is one sentence, under 25 words, that says what the reader can do here.

Keyboard and ARIA

No interaction. The title must be an <h1> so screen reader users can find it from the heading list.

Known issues

None known.

Section

.cai-platform-section

When to use

To group related blocks inside the main area with the same vertical space between them.

When not to use

For space between paragraphs of running text: the text styles already handle that. Not for side-by-side layout: use the grid object or the feature grid.

How it works

A one-column grid with the section gap token between its children. Use it on a <section> when the group has its own heading, or on a <div> when it does not.

Content guidance

Give each <section> a heading, and name it with aria-labelledby pointing at that heading.

Keyboard and ARIA

No interaction. A <section> with an accessible name becomes a region landmark; one without a name does not.

Known issues

None known.

Action group

.cai-platform-actions

When to use

For two or three related actions together, such as a primary and a secondary button after a form or in a hero.

When not to use

For navigation menus or long lists of links: use a <nav> with a list. Not for more than three actions: the reader cannot tell which one matters.

How it works

A wrapping row with a fixed gap. Below 480 px the actions stack and take the full width, so each one stays an easy target.

Content guidance

Put the main action first. Each label starts with a verb and makes sense on its own: "Save details", "Browse the components". Use <a> to go somewhere and <button> to do something.

Keyboard and ARIA

Tab moves through the actions in source order, which is also the visual order. Each control keeps its native keyboard behaviour.

Known issues

None known.

Feature grid

.cai-platform-feature-grid

When to use

To show a short set of features or options of equal weight, each in its own card.

When not to use

For data that readers compare across rows and columns: use a table. Not for a single item, or for items with a clear order: use a list.

How it works

A two-column grid that becomes one column below 768 px. Each child is usually a .cai-card.

Content guidance

Keep the cards parallel: a heading of the same level and one or two sentences each. An even number of items fills the two columns.

Keyboard and ARIA

No interaction of its own. If a whole card is a link, put the link on its heading text and keep the rest as plain text.

Known issues

None known.

Command block

.cai-platform-command-block, __cmd, __prefix

When to use

To show one terminal command that readers copy, such as an install command.

When not to use

For several lines of code or output: use a code block. Not for commands the reader must edit before running without saying so.

How it works

A box with the command in <code> and a native copy button. The prompt sign is decorative and cannot be selected. Without JavaScript the copy button is hidden and the command can still be selected and copied.

Content guidance

Show the command exactly as it should run. Name the copy button by what it copies, for example "Copy install command".

Keyboard and ARIA

Tab reaches the copy button; Enter or Space copies. The result is announced in a polite live region.

Known issues

None known.

Footer

.cai-platform-footer

When to use

At the end of the page, for ownership, licence and a few secondary links.

When not to use

For the main navigation or for content readers need to complete a task: put those in the header or the main area.

How it works

A <footer> with a top border that spreads its children across a row and stacks them below 768 px.

Content guidance

Keep it short: who made it, the licence and two or three links whose text says where they go.

Keyboard and ARIA

No interaction of its own. As a direct child of <body> the native <footer> is the contentinfo landmark.

Known issues

None known.

Image

.cai-platform-image, --4x3, --3x2, --1x1, --21x9, --9x16

When to use

To show an image in a box of fixed shape, such as a card cover or an article header, when the image may be missing: content from people or a content system, or a page built before its images exist.

When not to use

For an image that must keep its own shape, such as a chart or a screenshot: the frame crops it. For icons and logos: use an <img> or an SVG at its own size. Never to stand in for an image that carries information: if it is missing, say so in text.

How it works

A <div> of fixed aspect ratio, 16:9 unless a modifier sets another, around a native <picture> with AVIF and WebP sources and a JPEG <img>. The image fills the frame and is cropped to it. A frame with no image shows an abstract placeholder in the colours of the vejer theme, chosen in AVIF, WebP or JPEG with image-set(). In dark mode it shows a night version; high contrast keeps the day version. No JavaScript is involved. While an image loads, or if it fails, the frame shows a flat surface, and a failed image's alt text is drawn on it. Transparent PNG and SVG images sit on that surface too. Without CSS the image shows at its own size. The placeholder files ship in dist/placeholders/: every ratio at 640, 1280 and 1920 pixels on the long side in AVIF and WebP, at 640 and 1280 in JPEG, and two SVGs, day and night, that fit any size. Point your own <picture> at them to show the placeholder on purpose.

Content guidance

Give every real image an alt text that says what it shows, in one plain sentence. If the image is decorative or the text next to it already says the same, use alt="". Never describe the placeholder: it is a background and nothing reads it out. The frame crops the image to its ratio, so keep text and essential detail away from the edges, and describe what stays visible. Set width and height on the <img> to the image's own size so the page does not jump while it loads. Add loading="lazy" only to images below the fold; leave it off a hero or any image visible when the page opens, so it loads at once. Do not put text in images.

Keyboard and ARIA

No interaction of its own. Screen readers announce the <img> by its alt text and skip the placeholder; an empty frame announces nothing. Do not add a role or an aria-label to the frame. If the image is a link, the link takes its name from the alt text, so the alt text must then say where it goes.

Known issues

In forced-colors mode browsers drop the placeholder, and the frame shows a thin border instead. If an image fails to load, some browsers add a broken-image icon next to its alt text. The night version follows a dark mode set on a page or a section, but not a light section inside a dark one.

Source & build

Platform source lives in packages/platform/src/. Never edit dist/ directly.

File layout

packages/platform/
├── src/
│   ├── components/
│   │   └── _components.css   ← all .cai-platform-* classes
│   ├── index.css             ← @import entry
│   └── platform.js           ← reserved entrypoint (no-op)
└── dist/
    ├── platform.css          ← generated, do not edit
    └── platform.js           ← generated, do not edit
