        CAI aims for WCAG 2.2 level AA. What is checked on every change, what has not been tested, and the known issues. Last reviewed on 13 October 2026.

        Target

        CAI aims to meet WCAG 2.2 level AA, the level that EN 301 549 and the European Accessibility Act refer to.

        A design system cannot make a service accessible by itself: how you use the components decides the result. Each component page says what is yours to do, under Keyboard and ARIA and Writing the content.

        What is checked on every change

        • An automated scan with axe-core of the home page, in English, Spanish and Arabic, and of every page of the documentation, in the light, dark and high-contrast modes. On component and pattern pages the scan runs once with each tab open, and on a sample of pages once with the search dialog open, with results and with none. A serious or critical finding fails the build.
        • Keyboard use of the sidebar drawer, the modal dialog, the tabs, the Code and Design tabs of the component pages, the "On this page" index, whose links open the tab of the section they point at, and the search: Ctrl+K, the arrow keys through the results, Enter and Escape.
        • The pages with JavaScript turned off: content is readable at 320 pixels wide, the Code and Design sections of a component page show one after the other, the search button is a link to the A–Z index, and no control that needs JavaScript is left on screen doing nothing. The color mode switcher in the page footer shows as three radio buttons, which still set the mode. The language switcher of the home page opens its list of languages, which are links, with the popover API and no script.
        • Reduced motion: no transition or animation runs when the visitor asks for less motion.
        • Forced colors: a focused button and a focused search result keep a visible outline, the selected tab keeps its underline, and the search dialog keeps its border.
        • The home page in Arabic, right to left: it must not overflow at 320 pixels wide, with JavaScript or without it.
        • Right-to-left text: the demo of every component, except the player, is laid out with dir="rtl" next to its left-to-right layout. Each element with text, and each control, must sit where the mirror image puts it, and nothing may overflow. The check runs with and without JavaScript.
        • Contrast of the text written for the home and documentation pages, in all three modes.
        • Before this release, the same automated suites ran once in Firefox 155 and in WebKit 26.6 and 27.2 (the engine of Safari), on Linux, and their findings were fixed. They do not run on every change, and neither is a test on macOS or iOS.
        • Contrast of every token pair a component draws, by a script, in the three base modes. A theme of your own is measured by the same script, as the themes page shows.

        What has not been tested

        • Screen readers. No assistive technology has been used to test this release: NVDA, JAWS, VoiceOver, TalkBack and Orca have not been tried. Nothing here says a component works with them.
        • Speech recognition and screen magnifier software.
        • Right-to-left text by a person who reads it, or with a screen reader. Only the layout is measured by a script, and the player's controls are not part of that measurement.
        • Zoom to 400 percent by hand. Only the 320 pixel width is measured.
        • Research with disabled people.

        Automated tools find only part of the problems. Treat this list as the gap, and test your own pages.

        Known issues

        • Tooltip. Escape does not close it. This partly fails WCAG 1.4.13 (Content on hover or focus). Keep tooltips non-essential.
        • Modal. Its buttons use the command and commandfor attributes. In a browser without them, and without JavaScript, the open button does nothing.
        • Player. MIDI needs JavaScript and Web Audio. Without them the player shows a message. On this documentation site, the example video's caption files load only with JavaScript; without it the browser lists the tracks but shows no text.
        • Select. The open list is the browser’s or the system’s, so it looks and sounds different in each. Where the browser supports appearance: base-select (Chrome and Edge 135, Safari 27), CAI styles the list too, and that list has not been tested with a screen reader yet. It works without JavaScript.
        • Linked card. The link in the title covers the whole card, so the body text cannot be selected with a mouse. Keyboard selection, find in page and screen readers reach it as usual.
        • Table sorted in the browser. The sorted column is exposed with aria-sort on its column header, and each sort is announced in a status message. Tabbing through the headings announces the column name; the sort state is read on the header cell and in the status message. Checked in the Chromium accessibility tree only; not yet tested with NVDA, JAWS, VoiceOver, TalkBack or Orca.
        • Avatar with a photo. If the photo does not load, the browser draws its text alternative inside the box, in capitals, and a long name can spill past it.
        • Code and Design tabs. The tab you chose last opens after the page has loaded, so the content below the tabs can move once.
        • Find in page. In browsers that do not support hidden="until-found" (Safari before 26.2, Firefox before 139), find in page (Ctrl+F) does not find text in the tab that is not open. In Safari 26.2 and later it opens the tab but does not scroll to the match. Open the other tab, or turn JavaScript off to see both.
        • Search shortcut. Ctrl+K (⌘K on a Mac) opens the documentation search instead of the browser’s own web search box. Use the browser’s address bar to search the web. The shortcut is shown on the search button, does nothing while you type in a text area or editable content, and there is no single-key shortcut. In a one-line text field it still opens the search, so on a Mac it replaces Ctrl+K, “delete to the end of the line”, there.
        • Search. It has not been tested with a screen reader. The number of results is announced once you stop typing.
        • Search at 400 percent zoom. The whole search dialog scrolls, so the search field can move out of view while you read the results. Shift+Tab or the Up arrow from the first result brings you back to it.
        • Language switcher. The list of languages opens at a fixed place under the header, not next to its button. Below 360 pixels wide its button shows a globe only; the language’s name is still the button’s accessible name. It has not been tested with a screen reader.
        • Site header menu. On narrow screens the site menu opens as a panel under the header. If you keep pressing Tab after its last link, focus moves into the page and the panel stays open over it. Press Escape to close it. (WCAG 2.2 success criterion 2.4.12, level AAA; level AA 2.4.11 is met.) The panel opens under the header's height at the default text size: with enlarged text and a header that wraps to a second row, it can cover that row.
        • Site header, enlarged text. A sticky header keeps a field reached with Tab clear of it by a minimum height. That works at 100 and 200 percent text. At 300 percent text, when the header wraps to several rows, Safari can still leave the field partly under it; Chrome, Edge and Firefox keep it clear. The Site header page says how to set the padding for your own header. In Firefox with forced colors the dim layer behind the open menu is not drawn; the panel keeps its border.
        • Section band. A band cuts off whatever sticks out of it above or below, so a tooltip on the first control of a band is clipped at 200 percent text and larger; start the band with its heading. The hover of an outline or ghost button on a band shows no change. In forced colors the band has no tint, only two thin rules above and below it.
        • Table of contents (cms). The mark on the section in view comes from core's script; without it, no link is marked, and the links still work. Next to the text, the contents list the sections at the inline end but come first in the source, so Tab reaches them before the text. It has not been tested with a screen reader.
        • Copy button. When the browser refuses to copy, the failure is announced to screen readers, but the button shows no message.

        Report a problem

        If something does not work for you, open an issue on GitHub and say what you were trying to do, the browser and the assistive technology you use.
